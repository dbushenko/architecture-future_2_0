# Моделирование домена и интеграций

## Домены

### Управление пациентами

**Ответственность**: Регистрация, верификация, хранение личных данных пациентов. Не содержит медицинских данных.

**Агрегат**: Patient Management

Публикуемые события:

- *PatientRegistered* — новый пациент зарегистрирован
- *PatientProfileUpdated* — изменены контактные данные

Потребители событий:

- *Payments* — создать финансовый счет
- *Reporting* — обновить метрики по новым пациентам
- *Scheduling* — предзаполнить данные для записи

### Медицинские процедуры

**Ответственность:** Назначение и проведение медицинских процедур, фиксация результатов. Не содержит персональных данных, только медицинские.

**Агрегат**: Medical Procedures

Публикуемые события:

- *ProcedureOrdered* — назначена процедура/исследование
- *ProcedureStarted* — начало проведения
- *ProcedureCompleted* — процедура завершена, результат получен
- *DiagnosisEstablished* — поставлен диагноз

Потребители событий:

- *Payments* — выставить счет за процедуру
- *Inventory* — списать использованные материалы

### Финансовые операции

**Ответственность**: Выставление счетов, прием платежей, управление кредитами.

**Агрегат**: Payments

Публикуемые события:

- *InvoiceGenerated* — выставлен счет
- *PaymentReceived* — платеж поступил
- *PaymentFailed* — платеж не прошел
- *LoanIssued* — оформлен кредит/рассрочка

Потребители событий:

- *Reporting* — финансовая отчетность
- *Inventory* — оплата заказанных материалов

## Обоснование выбора событийного подхода

Событийный подход кардинально меняет способ интеграции. Вместо жесткой оркестрации через умную шину Camel, где вся логика процесса централизована, мы переходим к хореографии — каждый домен сам реагирует на события и публикует факты своей работы. Это дает три ключевых преимущества.

- *Гибкость*: новые бизнес-направления (например, фармацевтическая компания) подключаются простой подпиской на нужные события, без изменений в системах-источниках, что сокращает time-to-market с месяцев до дней.
- *Масштабируемость*: Kafka позволяет горизонтально масштабировать обработку до сотен тысяч событий в секунду, тогда как Camel и монолитный DWH становятся узким горлышком при росте нагрузки.
- *Скорость реакции*: вместо ночных ETL-процессов в DWH данные поступают в витрины в near-real-time через потоковую обработку (Kafka Streams), сокращая формирование сложных отчетов с часов до минут. Кроме того, события сохраняются в Kafka как неизменяемый лог, что дает полную историю для аудита и позволяет «переигрывать» данные при появлении новых потребителей — то, что невозможно с очередями Camel, удаляющими сообщения после обработки.
